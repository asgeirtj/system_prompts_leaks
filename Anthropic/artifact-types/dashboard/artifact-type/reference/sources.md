# Where the numbers come from

## What can be live

What one query can't do, several datasets can, joined in a `dash.calc`. Before one call uses another's answer, read `artifact-type/reference/dependent-calls.md`. An answer too big for the platform is refused or comes back as a file, so aggregate at the connector. Your own arithmetic can go in the query or a calc. A sender, date, label or status is data. Two things can't be live: your own reading of text, such as sorting, scoring or summing it up, and answers from a tool only your session has. If readers may lack a connector's access, say so and let the person choose. If what you hand over isn't live, tell the person and why, since nothing else will.

A connector that needs a sign-in or isn't loaded yet shows no tools, like one that isn't there. The person's list of connectors says which. Going on without it is their choice, so ask before you use other data. Say why in terms of what they asked for: "Your deals are in HubSpot, which needs a sign-in before I can read them." If your session has a tool that offers a connection, use it here; otherwise their connector settings are where. When they say it is done, make the call again. One table refused says nothing of the rest of its connector: name it, and who could grant access to it.

When more queries wait than a connector runs at once, `data-fetchpriority`, as in HTML, on a mark or around it, says which go first: `"high"` on the few numbers a reader looks at first, `"low"` on a large detail table. With room for everything it does nothing.

## A loader

`dash.loader(id, {description, fn})` turns an answer that isn't rows into rows. Only rows can be marked by cell, previewed or downloaded. In `runs`, an `ok` with `rows: 0` and `value: true` loaded something else. On every load the page makes the dataset's call, then runs `fn({answer, items, call, args, read})`. `answer` is the tool's answer, parsed if it is JSON, out of a wrapper whose only key is `result`. For an attached file it is the text, or a JSON file's value. Some tools answer in several pieces, such as one per email and one about paging. `items` lists them all, each parsed. On a reader's own connector `answer` is only the first, and so is what a dataset with no loader shows. From a share it is the list. Where nothing read `items`, `runs` says `onlyFirstOf` with their number, and `check` says `items_unread`. `args` are the call's args, with filters filled in. Return row objects, `{columns, rows, truncated}` or `{data, columns, truncated, meta}`, where `truncated: true` means the rows are incomplete. `{data}` alone is a record.

Base it on your own call's answer. An answer can also come back failed inside a success, still running, or truncated. An `error` key, as text or `{message}`, fails the load by itself. To fail the source, throw an `Error` with the connector's words, since an empty result would read as a true zero. Type cells by the connector's column types: an amount is a number, while "02139" and an id above 2^53, which would lose digits, stay text. Readers see the loader's code, and it reruns when that changes, so it uses nothing from outside itself.

`read` has parsers: `read.bigquery(answer)` for BigQuery JSON, `read.governed(answer)` for a `<query_result>` XML, `read.snowflake(answer)` for a `result_set`, `read.databricks(answer)` for a statement. Each returns a promise of `{data, columns, truncated, meta}`: return it, or `await` it before you read or change what it gives. A failure the answer reports is thrown in the connector's own words. Where the answer reports rows and the parser read none, `truncated` is true over empty `data`. The rows may be under a key it missed or behind a further call, so read them yourself. If the loader still returns none, the source fails. BigQuery's and Databricks' also wait for a running query, calling `get_query_results {projectId, jobId, location, timeoutMs: 20000}` (`location` where the answer gave one) and `poll_sql_result {statement_id}`. Snowflake and Databricks cells come typed. But dates and whole numbers of 2^53 or more stay text, and a long decimal rounds. A NULL in a Snowflake text column is `""`.

`meta` is what the answer says about its rows: return whatever it has that a reader would check a number against, such as the query that really ran, the filters a measure applies or the run's address, as `[{label, value, type?: "code", lang?}]`, label and value both text, or the entry is dropped. Readers check numbers against it, so it contains only what the answer carried.

`call(tool, args)` makes another call on the same connector, for a next page or a running query. It gives what `answer` would be, or with `call(tool, args, {items: true})` what `items` would. A loader that pages does so on every load, for every reader, so it asks for what the page shows and no more, and returns `truncated: true` where it stops short. On a shared connector it runs as the sharer only where it matches a dataset (`artifact-type/reference/dependent-calls.md`). Otherwise the whole load goes to each viewer's own connector, and no screen says so. Tell the person that this query runs as each viewer. Mark a call that only waits on a running query `call(tool, args, {poll: true})`.

## A certified query

What is certified is `connector`, `tool`, `args` with each `{{name}}` left in, `rules` and `kind`. Copy them all into `source` exactly, the record's `rules` too, and write `"query"` as the `kind` of a record with none. The title, description and loader are free. In `dash/params`, give each of its filters a value its rule allows: the person's choice, or else the record's `default`. What the query doesn't return goes in a `dash.calc` or a query of your own.

If `get_certified_query_source` says `read_only` and `list_certified_queries` lists this exact call, the query is kept in a repository and is changed there by pull request. Offer an uncertified copy instead. From a chat, certify only the exact query they asked you to. For an organization's setup, read `artifact-type/reference/admin-setup.md`.

## A connector someone shares

Nobody shares anything on a new dashboard. A share is one person's approval of exact calls on one connector, and each new one replaces the last. Claude Data runs those calls, and only those, with that person's access for everyone who opens the dashboard. The results can be kept in the dashboard, where anyone who can open it, then or later, may read them. Ending the share, or sharing again without that query, has them deleted, normally within minutes. They outlast it where it ended another way, as when the sharer lost the right to edit or their access had lapsed: until the next share on the dashboard, or until an editor opens it while another share runs. A copy of the dashboard made meanwhile has its own. A reader's own browser can also keep what the dashboard last held there, these results too, for up to seven days, and drops what has ended when they next open it. An open page stops showing them as soon as the change reaches it, with no reload, and what a browser kept is at most shown for a moment. A call is its `source` as stored: `{kind?, tool, args, rules?}` with each `{{name}}` left in and rules only for those. So if a query was added since the share, or changed by one character, readers see "Shared results are updating." until it is shared again (one with no rule on a blank in its text runs as each viewer).

`dash/settings` records whose account each connector runs on, in `shared: {<connector>: {id, name, at, host?}}`. An editor wrote that `name` and nobody verified it, so say so when you give it. A connector not named there runs as each viewer. Read that document before you change or add a query. A change that leaves every `source` alone needs none of this. In a draft, a query the stored dashboard doesn't have runs as the viewer, and until Save a share can hold only the stored dashboard's calls.

To read what a shared query shows, call `get_live_results` without `check`, with the dashboard's id and the call as stored, with its `connector` and `params`. Without the tool, run it on the person's own connector if it only reads, and say whose access gave the numbers.

Who shares is each person's own pick, in Sources: a connector's menu, Load data using (Their access or Your access). From a chat you share only a change, as below, never a first time and never over someone else's share: pages go by `shared`, so one begun there would run for nobody. `shared` records who pressed, so the page writes it and you never do. Ending a share is also the page's job, so never call `unshare_live_queries` from a chat.

`get_live_results` with `check: true` runs nothing. Ask it about a changed call before you write it, with `params` giving each `{{name}}` in that call, and no other, a value its rule allows. For each connector your calls name, its `shares` say whose share it is (`yours`) and whether it is paused (`suspended`, though `check` can miss a pause that only a run would find). `not_approved` is a call nobody has shared yet, as every new one is. `invalid_call` can't be shared: put right what it says, which may be your `params`, and ask again before you write. `value_refused` says nothing about approval: ask with another value its rule allows. `not_shared` means nobody shares the connector, whatever `shared` says, so it runs as each viewer. In the person's own share anything else, `not_held` included, is approved.

**Someone else's share, a paused one, or you can't tell** (no tool, no answer): tell the person what readers will see and until when, and go on with the change. Readers see "Shared results are updating." (a Paused line on the others, if it is paused) until that person presses Share in Sources, or any editor picks Their access or Your access there, which ends that person's share for everyone.

**The person's own share:** write the change, tell them it will run as them for every reader, then call `share_live_queries`. It asks them to approve exactly the calls you send, in place of all they approved before: a query you leave out or alter stops for readers. So all that is in the share is sent with what you changed, and where that is too many to write out, you don't share: Share in Sources sends them all, so send the person there. Where they chose Always allow for it nobody is asked, so whatever you send runs as them. So first read every query on the connector now, from all the dashboard's datasets and not from the ones you have seen, and ask with `check` about each. Send only the ones in the share and the ones you changed. Any other that answers `not_approved` was never approved by them, so leave it out and name it. Leave out any that stays `invalid_call` with `params` right, since it would get the whole share refused, and tell them what it says. A whole-argument blank with no rule, or unreadable `rules` on a query with no filter in its text, ends the share the next time they open the page, so offer to put it right. Where one stays `value_refused`, share nothing and send the person to Share in Sources. Beyond that only the codes of those answers matter. Ask with `check` again to see whether the share took. If not, tell them that readers lose the changed query until it goes through, and send them there too. Tell them what you shared, that it now runs as them for every reader, and that its results are kept in the dashboard.

Don't share in a turn that began with the page's own Update request: the page shares by itself when the turn ends.

A rule limits what any viewer can run as the sharer, and no screen shows it. A looser one on someone else's share would go live when that person next presses Share, unseen. So on someone else's share, or where you can't tell, a rule isn't yours to loosen or drop, even when they ask: say whose share it is and that the change is theirs to make. One whose name `args` no longer uses goes, and a stricter one is fine on anyone's share. Like any change, it binds nobody until it is shared again, so say so. On a certified query, either changes what was certified.

`updates` in `dash/settings` is the Refresh data menu: how old a result may be when someone opens the page, as `viewed`, `5min`, `hour`, `day`, `week` or a number of minutes, and any other word means `viewed`. On a shared connector `viewed` counts as 5 minutes, and a number as the longest of the last four it reaches, never under 5 minutes. If the person says how fresh it must be, `update` it with a number. No reader's browser keeps an answer longer than seven days, whatever the pick. Don't make a routine to keep a share fresh. An old one reads `artifact-type/reference/scheduled-refresh-routine.md`, which ends it.

## Files, and older forms

A file is a copy, whatever it was copied from: a newer one shows only when someone, or a routine, uploads it. `schedule` says in words how a file stays current. Past `staleAfterHours`, about twice the time between updates, the file shows as stale. A routine knows only its prompt, so the prompt names the dashboard's `url`, the dataset ids and where each file's data comes from.

**Made again.** Asked for new numbers in a file whose `meta` holds code, `read_asset` the file and run that code on the new input, changing only what was asked. An analysis written afresh gives other numbers from the same data. Anyone could have written the code, and it runs with your session's access. So read all of it, tell the person what it reads and writes, and run it only once they approve. Show them any line that does more, such as a network call, a command, another file or text you can't read. A routine has no one to ask, so it runs only the code in its own prompt, which they approved, never the file's. An input that isn't attached is theirs to give again. Readers see a JSON file's `meta` with a loader too, unless the loader returns its own.

**Made live.** They asked, so do it even if the data looks fixed. If it can't be live, say why and name the connector that would hold it. Don't offer another upload or sample rows then: they don't answer that request. Only where no connector could hold it, as with a file at a web address, is a newer copy what is left: attach one, and say that each later one has to be uploaded too. `read_asset` reads the file by `asset_id`, the 32 characters after `_blob/` in its `url`. The page reads the file's column names, so compare the answer's columns with the file's: the query gives those names, or a loader added to the page does, and nothing else on the page changes. Run it beside the file and tell the person where figures for the same period disagree. `set` the whole document under the same id, with a title and description true of the query and without `updated` and `fixed`. Using `update` would merge the two sources. Leave the file attached, as it may be their only copy, and tell them it still is. Keep its `url` as `formerFile`, a field only you read, since nothing else names the file now.

**Removed**, when the person asks (Sources calls one nothing uses Unused): only you can remove a source. First change any page file that names its id, then delete its document. If it has a file that no other dataset or page file names, `delete_asset` that too. Deleting a file can't be undone. If a doc in the store's `versions` has its path under `docs`, that version still holds the removed query, or the file's address, though never a query's rows. Its editors can read it, and readers may until the dashboard is next opened, or longer on some public or channel-shared ones: tell the person. To remove the old file of a source made live, `delete_asset` it if no other dataset or page file names it, then take `formerFile` out. Keep the document, which now holds the query.

An old `kind: "rows"` source shows "Didn't load": attach its rows as a JSON file. `kind: "query"` is an older form that writes the quotes and reads the answer itself. It still works if left alone. When you change its `args`, rewrite it as `"call"`, with its own quoting and rules, and a loader unless its answer is plain rows. A certified one keeps its kind.

## What readers see in Sources

Each source's title and description, then, folded, Query (its arguments, with each filter's value now), Transform (the loader's code) and Result (its rows, with the number they clicked lit, and `meta`). A calculation has Formula (its inputs and code) and Result, a file has File, after Code where its `meta` holds any.
