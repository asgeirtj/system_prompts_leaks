# Latency Levers - What Each One Moves, and What It Risks

> **Reference for `shared/latency-optimization.md`**: one entry per lever. Read it when the guide sends you here, and go straight to the heading you need.

---

## How to use an entry

**Fetch a lever's row before proposing it** (the rows are in `shared/live-sources.md`): availability, parameters, headers, limits and prices are left to the page on purpose. A bare list of options states none of these, so it needs no fetch; a list of links checks only that each page loads. If a fetch fails, say so. Where the lever's entry names another file of this skill for those facts (`shared/prompt-caching.md`, say), use it and label its facts "cached, not verified". Otherwise state no figures: size the change as largest / medium / small.

**The expectations below give the direction of each effect, not its size**: seconds vary by model, account, platform, region and time of day. Where a page's general advice and a method here point different ways, say so and let the eval decide.

**The levers come in three kinds, by what they risk**, and where neither the user's request nor the profile sets an order, test them in this order: **request and display settings** (caching, streaming and thinking display), which aim to shorten the wait, or the part of it anyone sees, without changing what the model can do; **loop and output changes** (input tokens, the agent loop, output tokens), which change what the model sees or writes; and **tradeoffs** (fast mode, effort, model choice, thinking off, limits on the longest task), which exchange dollars, capability or answers for seconds. No kind skips the eval. How each is timed: `shared/latency-optimization/measuring.md`, "The cheapest route that can see a change".

## Input tokens - give the model less to read

Every uncached input token adds to TTFT, on every call that sends it. Where the wait that matters is a first-token one, trimming the prompt is a latency lever; where it is the whole task, most of the time usually goes to writing output, and a shorter prompt mostly saves cost.

- **Trim it.** Remove the parts of the prompt the task doesn't use. For instructions, skills and tool descriptions written for older models, run the `prompt-audit` subcommand (`shared/prompt-audit.md`); it can lengthen an under-described tool, so time its diff like any other. Send images at the resolution the task needs (the **Vision** row). In a long conversation, context editing (the **Context Editing** row) clears older content on the server; each clear restarts the cache at that point, so clear enough at once to make each restart worth it, and check recall on the eval.
  - Context editing with a message thread: read the Message threads entry first.
- **Defer it.** Tool search (the **Tool Search** row) keeps deferred tool definitions out of the model's context until it loads the ones it needs; skills do the same for instructions (the **Skills** row under Tools).
- **Make access efficient.** A tool that returns the page or the fields a task needs keeps the rest of a long document out of the context; for tabular data, code execution (the **Code Execution** row) lets the model query a file in a sandbox.

Each of these can add a call, or tokens elsewhere, and the model may spend turns fetching what it previously read inline, so let the eval decide which to keep. They edit `system` or `tools`, so make them between conversations (next entry).

## Prompt caching and an append-only prefix

For design and placement, read `shared/prompt-caching.md` and follow its workflow, and fetch the **Prompt Caching** row for current durations, limits and prices; do not improvise `cache_control` markers. What matters for latency:

- **A cache read skips reprocessing the prefix, so TTFT drops on every call that reads it.** The time saved grows with the part of the prompt that is cached: on a short prompt it can be too small to measure even where the cost saving is large, and on a long one it can be large. Where the seconds don't move, it is not a latency lever for this workload, and whether to keep it for cost is `cost-optimize`'s call.
- **Static content first, then whatever varies.** The move changes the prompt, so check it on the eval.
- **Pre-warm only where the first request after a quiet spell is user-visible** (`shared/prompt-caching.md` § Pre-warming the cache). A longer cache duration and keep-alives serve the same gap (`shared/prompt-caching.md` § Choosing the TTL). All three are billed: list the cost beside the seconds saved.
- **Hold the configuration steady, and keep history append-only**: a change to the model, the tools or a request setting, or an edit to anything already sent, can restart the cache (`shared/prompt-caching.md` § Invalidation hierarchy). Use the append-only forms instead - a mid-conversation system message (the **Mid-conversation System Messages** row) rather than rewriting `system`, per-message effort rather than a top-level change. Where history has to shrink, context editing or server-side compaction restarts the cache only when it clears or summarizes, where client-side trimming on every turn restarts it every turn. If the code edits history, offer the `preserved-thinking-migration` subcommand (`shared/preserved-thinking-migration.md`; which edits the API checks: the **Preserved Thinking** row).
- **Verify from usage, not code review** (`shared/prompt-caching.md` § Verifying cache hits); where cache reads drop for no visible cause, the **Cache Diagnostics** row shows what changed.

## Message threads - stop re-sending the conversation

Caching spares the model from re-reading the prefix, but every call still uploads the whole conversation, and the API handles all of it again before the model starts. A message thread lets each call after a conversation's first send only its new messages. For the request shapes, the fields a thread holds fixed, what it doesn't support, its errors and the SDK helper, read `shared/message-threads.md` and fetch the **Message Threads** row; do not improvise the `thread` field. Retention is the user's decision, so link that part of the page beside the proposal. What matters for latency:

- **It may already be on.** An SDK helper or tool runner can add `thread` itself (the page says which do), so look at a request as sent, not only at the code.
- **It moves TTFT as the client sees it, on every call after a conversation's first.** The model still reads the whole conversation and a thread caches nothing, so measure it on top of caching, not instead of it.
- **It suits many calls over one growing, append-only history**, with gaps between calls (tool time and the user's pauses included) shorter than a thread lasts, and something heavy to leave out: a long accumulated prompt, large payloads, a slow uplink. It can't move a one-call task, a wait measured on a task's first call, or code that rebuilds history. On short prompts expect "can't tell".
- **It holds part of the request fixed**, so it clashes with a lever that changes a setting mid-conversation (a model router, a top-level change of effort or thinking, an edit to `system` or `tools`) or sends one call twice (a hedged request, a client retry). Check every lever in play against the page's field rules and its unsupported features.
- **Where it excludes a lever the workload needs** (context editing and compaction are for the same long conversations), measure the two as alternatives; in a search they are alternative combinations. What the page offers in that lever's place changes what the model reads, so check recall on the eval again.
- **It can fail silently.** When a continue can't go on, the whole conversation is sent again, which is slower than no thread at all, and an SDK helper may do that, or drop the thread, with no error reaching the code. Count the large requests after a conversation's first, from request bytes, and report the count beside every timing.
- **Measure whole conversations**, on the eval or in the application's own timing, with caching on in both versions; the probe can't, since each continue needs the last response's ID. A session can't see an organization's settings, so first confirm from a second request's bytes that the API accepted `thread`. Start the clock before the request is sent and measure over production's uplink, or the timing misses the very thing the lever removes. Read TTFT over the calls after the first, failed continues and retries counted in, with request bytes per call beside it: bytes vary far less than seconds.

## Agent-loop efficiency - fewer calls, and calls that overlap

For a multi-turn agent the dominant term is often the number of calls: each call pays its own TTFT.

- **Prefetch what the application already knows.** When the first tool calls of a task are predictable, run them before the first model call and put the results in the first user turn. Expect it to move the typical wait more than the slow tail. It adds input tokens to the calls that remain, and the first call may then think before its first output, so check time to first visible output too if anyone waits on it.
- **Return more per call.** Bigger pages, or tools that accept several IDs at once, let a heavy task finish in fewer calls. Balance this against input tokens and context growth.
- **For a job whose finish time matters: run independent tasks concurrently, and pack several items into one request** where the task allows. The job's time is then bounded by rate limits (the **Rate Limits** row). Packing changes what the model reads, so quality per item is checked on the eval.
- **Execute parallel tool calls concurrently, and return them together.** Where the model calls several independent tools in one response (the **Parallel Tool Use** row), the latency only disappears if the application runs those calls concurrently rather than in a loop, and returns every result in a single user message, before any text. Check that the code doesn't disable parallel calls. Tools with side effects or ordering requirements may need to stay sequential.
- **Start read-only tools as their calls finish streaming.** In a streamed response each tool call ends with its own `content_block_stop` event, so the loop can start an independent, read-only tool then rather than after the whole response - a deliberate exception to SKILL.md's rule of checking the stop reason before running a tool, which is why it is limited to read-only tools. Validate the parsed input against the tool's schema first, and discard the result if the response then ends with a `max_tokens` or `refusal` stop reason (SKILL.md -> Defaults).
- **Run independent subtasks concurrently, as subagents.** Run each piece as a separate request with its own context that returns only its finding; the task then waits for the slowest piece rather than the sum. The subagents' model and effort are a separate choice from the main agent's: match them to the subtask, and judge on the whole task's seconds, quality and cost rather than the subagent's own. Subagents can add cost, since each reads its own context, and the user's cost limit applies to the whole configuration, main agent and subagents together. Requests sent at the same moment don't share a cache (`shared/prompt-caching.md` § Concurrent-request timing).
- **Take steps off the model that don't need it.** A format conversion, a lookup by key, or arithmetic the application can do needs no model call. Where a run of tool calls needs no reasoning in between, programmatic tool calling (the **Programmatic Tool Calling** row) lets the model write one script that makes them all, so the model isn't sampled again until it finishes. It has a fixed overhead, so a job of a few small calls, or one where each call depends on reading the last result, gains little.
- **Make slow tools faster.** Cache results of repeated lookups, add timeouts, and move slow tools off the critical path where the task allows.
- **Long sessions: take compaction off the user's path.** Compaction (the **Compaction** row) replaces older turns with a summary the model writes on the server, and writing the summary is itself a generation, so the main lever is *which turn waits for it*. At a token threshold, the request that crosses it writes the summary first. Where the page offers an on-demand form, a separate request sent in the background, while there is still room, returns the summary and no turn waits. Compaction changes what the model sees, so check recall on the eval.
  - Compaction with a message thread: read the Message threads entry first.

## Output tokens - less to wait for

The model writes output tokens one at a time, so every token it doesn't write - thinking included - comes off the time to finish.

- **Specify the output shape**, ideally with an example, and the model stops narrating its way to the answer. For an agent, a tool the model calls to submit its final answer, whose schema is the output, is the tightest shape. Put what the user acts on first, so the early tokens are useful. A shape can also cut content the task needs, so validate it on the eval. In a multi-turn agent, shorter replies change what the user sees, and so can change what happens next: measure that on an eval whose user turns respond to the replies.
- **Enforce the shape with structured outputs** where a free-text answer would come with a preamble or need parsing (the **Structured Outputs** row). A new or changed schema pays a one-time wait while its grammar compiles, and a compiled grammar stays cached only for a while after its last use, so keep schemas and the tool set stable and don't generate schemas per request; changing the format mid-conversation also invalidates the prompt cache.
- **No commentary between tool calls.** Where nobody reads the text an agent writes between tool calls, an instruction not to write it is a candidate to test. It can cost quality, since commentary can help keep the model on track on long tasks. On models that write progress updates (the **Thinking** row lists them) those notes come back as thinking blocks, so read the target model's section in `shared/model-migration.md` first.
- **Reasoning requested in the reply** - "show your thinking", or a reasoning field in the output - adds output tokens and, on some models, risks a refusal; `prompt-audit` has the row and the replacement.

## Fast mode - faster output for dollars

Fast mode (the `speed` field on a request) is the first of the tradeoffs because it runs the same model, so it buys speed with dollars rather than capability. Fetch the **Fast Mode** row before proposing it. Read from the page what it speeds up; how it is rate-limited and whether fast and standard speed share cached prefixes (if they don't, a fallback to standard speed on a 429 is also a cold cache, so plan for 429s); what the price multiplier applies to; and what it can't be combined with.

The saving can vary with when it is measured, so measure it on this workload at the times of day that matter. Its cost counts against the user's cost limit, and wherever it is reported, what the changes that add no cost give on their own is shown beside it. In an answer to a question about it, name in one sentence the changes that add no cost and move the same term (fewer output tokens, through an output shape or a lower effort level, which need the eval as much as it does), so that the paid lever isn't the only answer.

## Effort - how much the model works

Effort sets how many tokens the model spends - thinking, text and tool calls, in proportions that differ by model - and in a loop it usually changes the number of calls too. A lower level trades some capability for fewer tokens, which shortens each call and leaves output speed about where it was. Sweep on the eval (mechanics: `shared/cost-optimization.md` § Effort and budgets); for seconds, interleave the levels in time rather than finishing one level before starting the next (`shared/latency-optimization/measuring.md`, "Comparing two versions").

- **Sweep only the levels the model accepts** with the `thinking` setting the code sends, above the default as well as below (the **Effort Parameter** row; SKILL.md -> Thinking & Effort). A higher level is a lever that costs money: what it adds per task counts against the user's cost limit. Defaults differ between models, so set effort explicitly.
- **Vary effort between user turns without breaking the cache.** When some turns of a conversation are routine and some hard, raise effort only for the turns that need it, with the per-message form, which keeps the cached prefix. Something has to decide which turns are hard: the task type where the application knows it, or a classifier, whose own wait and mistakes count. When a change takes effect and its restrictions: the per-message section of the **Effort Parameter** row's page.

## Model selection - a different speed, a different ceiling

Take the candidates from the fetched lineup (the **Models Overview** row), above the current model as well as below. A smaller model usually has a shorter TTFT and a higher output speed, but **a faster model isn't automatically a faster task**: one that writes several times as many tokens or takes more calls can give the speed back, one that thinks before its first output gives a later first visible output even with a shorter TTFT, and a more capable one sometimes finishes in fewer turns. So compare candidates in seconds per completed task, on the eval, with output tokens per task beside them. A larger model is a lever that costs money: what it adds per task counts against the user's cost limit.

- **Choose the model per conversation, not within it.** Different kinds of traffic can run different models. A router that switches models inside one conversation starts the cache over and, for many pairs of models, drops the earlier model's thinking (`shared/preserved-thinking-migration/causes.md` § Switching models mid-conversation); change effort within a conversation instead.
- **It is a migration.** Before timing a candidate, apply that model's breaking changes from `shared/model-migration.md` in a test runner or behind a flag, so it runs as it would ship; the full `migrate` workflow is for the model the user then moves to.

## Thinking off - the steepest capability trade

Some models accept a setting that turns thinking off, or turns off up-front thinking, at some effort levels; others reject it (the **Thinking** row; SKILL.md -> Thinking & Effort). Turning thinking off removes the thinking tokens, so it usually shortens the task - but it can cost a large share of quality, and some models move reasoning into the visible reply, so watch output tokens too. Turning off only up-front thinking is a lever on time to first visible output: it helps only where replies would open with a long think, and it can cost quality too. These settings may not combine with per-message effort (the **Effort Parameter** row says which).

## Limits, retries and hedges - bounding the slowest tasks

The levers above shorten the typical task and its p90, but none of them bounds the slowest tasks (p99). Which lever here fits depends on why the slow tasks are slow, so find that out first (`shared/latency-optimization/measuring.md`, "Match the change to the percentile").

Limits come in two kinds: a **stop** is enforced from outside the model, by the code or the API, and the model can't see it; a **signal** is a count the model can see and pace itself to, and nothing enforces it.

| Counts | Stop | Signal |
|---|---|---|
| Tokens | `max_tokens` (one response, by the API) | A task budget (across the loop) |
| Calls | A cap on calls per task (by the code) | A last-call message |
| Seconds | A task timeout (by the code) | The elapsed time shown to the model |

The two kinds work best together: a stop alone ends the task with no answer, and a signal alone doesn't hold when a call stalls. Pick the limit that matches the problem: seconds when a user is waiting, calls when loops are the risk, and tokens when replies run long. Set each above what healthy tasks need, first count how many recorded tasks it would have ended and how many of those were answered right, and check the eval, since pressure to finish can cost quality and a stop that fires costs an answer. A stop set there rarely moves p50 or p90; it is judged on the worst case. Before any signal the model sees, read the target model's section in `shared/model-migration.md`: some models read harness text inside or straight after a tool result as a possible prompt injection.

- `max_tokens` **is a backstop, not a tuning knob.** With thinking on it covers thinking and tool calls as well as text, so a low cap can end a request before any answer is written (the full rule: `shared/cost-optimization.md` § Output tokens). Where the **Reduce Latency** row's page suggests it as an output limit, use it only as this backstop.
- **A task budget** is one allowance shared by every request in the loop, which the model sees counting down (the **Task Budgets** row; how to set it: `shared/cost-optimization.md` § Effort and budgets). It limits seconds only indirectly, one that's too tight can make the model stop early or scale the task down, and a mid-task change invalidates the cache. It suits unattended loops.
- **A cap on calls, with a last-call message before it.** A cap is a crude stop for a loop that never finishes; tell the model on the turn before it that its next call is its last, so it answers rather than being cut off. Place it the way the clock is placed (next bullet): as a new message, or, in the in-message form, at the end of each of that turn's tool results.
- **Tell the model that time matters, and show it the elapsed time.** These two prompt changes aim at the typical task, not only the tail. The recipe, placement and measured effect are on the **Cost Optimization** row's page; where your placement differs from the one the page measured, its figures don't carry over. Show the elapsed time, against any limit, appended after the newest turn, never by rewriting earlier content, so the cached prefix still matches. The preferred form is a new message, a mid-conversation system message where the model accepts one (the **Mid-conversation System Messages** row); otherwise use the page's in-message form, at the end of the newest user message, and leave each earlier clock as sent.
- **Client timeouts, retries and rate-limit headroom.** Check the SDK's timeout and retry settings against the latency target (SKILL.md -> Other API Surfaces, Client config; the **Errors** row for what is retried), and keep rate-limit headroom (the **Rate Limits** row) so 429 retries don't become the tail.
- **Hedged requests** - a second attempt started at a deadline, keeping whichever finishes first. It is expected to help mainly where slow tasks come from sampling variance or stalls, since where they are slow because they are long the second attempt is long too. Each task that reaches the deadline pays for a second attempt (less if the slower one is cancelled), so the extra cost grows with the share of tasks that reach it. Use it only for operations safe to run twice.

## What the user sees while waiting - streaming and thinking display

These levers change how long the wait feels more than how long it is. Measure them on the time until the user first sees anything, keep time to first text and time to finish beside it, since a display setting can make the answer itself arrive later, and run the eval as for any other lever.

- **Streaming user-facing requests** (the **Streaming** row). It lets the reader start at the first visible output instead of the last.
- **Fill the thinking phase.** When the model thinks first, a streamed response can open with seconds of nothing. The `display` field on the thinking configuration decides what streams meanwhile: nothing readable, which can start the final text sooner (the thinking still runs in full; what can start sooner is the text after it); a readable summary, for a chat UI; or the short progress notes some models write between tool calls, for an agent UI (values, models and defaults: the **Thinking** row). A status line naming the current tool, or in a voice product a short spoken holding phrase when a tool call starts, fills the same gap from the application's side.
- **Act on long tool inputs as they stream.** With eager input streaming (the **Fine-grained Tool Streaming** row) on user-defined tools, an application can show a long input while the model is still writing it. The input can arrive as invalid JSON, so follow the rule in SKILL.md -> Defaults before running the tool. Keep anything shown early to actions that can be undone.

## Levers this file doesn't name

When the user is exploring, asks what's left, or wants a search, fetch the **Release Notes** row and the **Features Overview** row and scan them (in the release notes, the entries dated since the model the code runs now was released) for any feature, model or setting that isn't here and could mean fewer calls, a shorter TTFT, fewer output tokens, faster output, or less time outside the model. Both pages are long: use the web fetch tool with the row's lookup text, or save the page to a file and search it, rather than reading it whole into the conversation. Treat a find as a candidate like any other: read its own page, place it among the three kinds ("How to use an entry") by what it changes, and hold it to the same eval rule.
