# Function hooks: the long form

The long form of the plugin-authoring skill: what a plugin of function hooks is in full, where its exact contract is written down for the build you are running in, and where to look when something does not take. SKILL.md beside this file says where a mod is written, where the types are and what happens when the turn ends. Run `claude plugin validate <dir>` on the plugin's folder early and often: it reads the manifest and the hooks
module's source the way the engine will and reports what the module hooks and calls and everything the engine would refuse, before a
session loads it. The API is early access and moves between releases: the declaration file is the authority, this note the map.

## What a plugin of function hooks is

A mod is three files written directly: `claude plugin init` scaffolds another kind of plugin, one of command hooks under `~/.claude/skills`.

A plugin is a folder with a `.claude-plugin/plugin.json` manifest. Its
function hooks live in one hooks module: a TypeScript or JavaScript file
that `hooks/hooks.json` names under `modules` (one path, relative to that
file), exporting `register(on, options)`; the module, and every file it imports from the plugin, is named `.ts`, `.tsx`, `.jsx`, `.js`, `.mjs`, `.cjs`, `.mts` or `.cts` (a file named otherwise is not loaded) and is an ES module whatever its suffix. A file of the plugin is imported with an `import` declaration. A module holding `import()` does not load. `on(event, matcher?, hook)` adds a
hook; `options` holds the values of the fields the manifest's `userConfig`
declares. Every hook has the shape `($, e, next)`: `$` is the engine
interface (display, model, session, prompt, tools, filesystem, store,
clock, network, host commands, settings, environment, the config menu's rows and the rest), `e` is the event's input as a plain value,
and `next(e)` continues to the other plugins and then the engine's own
behaviour, resolving to the event's result. A hook that returns without
calling `next` answers for itself; one that calls `next({ ...e, ... })`
rewrites what the rest of the chain sees, within what that event allows.
The module runs in an environment of its own, with no DOM and no Node:
everything outside it is reached through `$`. JSX is available with `h` as the factory.

The events cover tool calls and their descriptions, the rows the conversation keeps (`session.append`), the prompt as submitted, the system prompt's sections and the first message's context blocks, what the interface
draws, the turn's start, steps and completion, the session's start, end (a /clear too: `session.end` with `reason: 'clear'`, and no `session.start` after it) and deliveries, each hooks module's admission, skills, subagents and attribution text. The settings hooks' own events are hookable as `classic.<Event>` (`classic.Stop`, `classic.SessionEnd`), `e` being what that hook receives on stdin, `transcript_path` and the other base fields included. Which of them a
feature is, and what it needs from `$`, are the two questions worth settling before writing. Two events stream, `turn.step` (a model request of the turn) and
`process.spawn` (a child's output, piece by piece; for the caller `$.process.spawn({ argv })` is the stream and the loop's end is the child's): a hook on either is an
async generator (`async function* ($, e, next) {}`, the one form that loads there); `next(e)` is the stream beneath, `yield* next(e)` forwards it and evaluates to the
result, `for await` over it rewrites the chunks one at a time, yielding without `next` answers alone, and a hook that fails mid-stream is left where it stood. A `telemetry` event is hooked by name (`telemetry.*` names them all; `*` and a negation do not select one), and the hook picks its stream in the matcher, `to` written as a string literal or a list of them (`on("telemetry.log", { to: "collector" }, hook)`): `collector` is the customer's OpenTelemetry collector, `anthropic` is Anthropic's own analytics and is the stream the plugins built into the CLI stand on, and `claude plugin validate` lists the streams a module's hooks stand on.

## The types are the reference

`types/claude-code.d.ts` beside this file is this build's declaration of the
whole API, written by the engine as the skill loaded: it declares the module
`claude-code` (import types from it; at run time the import is empty), the
globals a hooks module has, and the inputs of this build's built-in tools, so
`e` narrows per tool. Its header carries a `tsconfig.json` that fits a hooks
module and shows how to type `register` against `Register`. A mod the engine
loads from a folder it is being written in (this session's mods folder, or a
`--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` folder the session hot-reloads)
has the same declarations laid beside it, in `.claude-plugin/types/`, at every
load and reload: `claude-code/index.d.ts`, the API; `claude-code-tools/index.d.ts`, this
build's built-in tools; `claude-code-mcp/index.d.ts`, the MCP tools connected
when the mod last reloaded (refreshed when you save the mod; a restart
never replaces it); one entry per plugin its `plugin.json` lists under
`dependencies` (below); and a `tsconfig.json` its own extends, so its editor
and `tsc -p <mod folder>` type it with no step taken. There is no command to
run. A folder the session loads from and does not hot-reload (a `--plugin-dir`
under `claude -p` or an SDK host, an installed plugin's) is never written in: a
mod there is type-checked with the header's `tsconfig.json`, kept outside the
mod folder.
The built-in tools' table is what this build registers on this machine: a
tool another build has (Glob and Grep, which a native macOS or Linux build
does not register) is compared through `String(e.tool)`.

Read that file for every event's input and result, every noun and method on
`$` with its doc comment and example, every element each surface draws and
the props each element accepts, and the limits it states. Shapes there are
the engine's own, not the Messages API's: `$.session.messages()`, for one,
answers `SessionMessage` rows of `{ role, text, toolUses }`, not `content`
blocks. When the build updates, regenerate rather than edit.
`claude plugin validate <path>` reads a plugin's manifest and its hooks
module's source and reports what the module hooks and calls, which is the
quickest check that the engine sees what you meant. It knows the mod, not a session: what runs above a mod there can skip or change any of its hooks, so whether a hook ran is checked in the session, where the debug log (`claude --debug`) has a line `<plugin>: <event> bypassed by <plugin> (tier <tier>); beneath runs` when a plugin above continued past a hook, and, for the times it did so again in the ten seconds after that line, one line `<plugin>: <event> bypassed by <plugin> (tier <tier>) <count> more times in the last 10s`. Under what it hooks, a `gating hook with .catch:` or `gating hook without .catch:` line names each hook at a site whose answer can refuse what was asked (`tool.call`, `tool.check`, `prompt.submit`, `prompt.mention`, `config.set`, `plugin.register`, `command.run`, a call on `$`, among others; its JSON report lists them as `gatingHooks`; a `command.run` hook that answers its own command reads `answers its own command:` instead and is not in `gatingHooks`: its matcher names only commands the module registers on `$` by a literal name, and neither the hook nor its `.catch` reads `next`; a hook there with no matcher, on a command the module does not register on `$` or one Claude Code ships (a registration it refuses), or that reads `next` is listed as a gate like any other): a fact, never a warning, since a hook that fails there is skipped unless its `.catch` answers in its place, and which it should be is yours to decide. A plugin that adds a noun to `$` in `engine.create` ships that noun's types as a contract: one self-contained `.d.ts` (say `types/index.d.ts`) that exports the noun's types at its top level and declares the noun on the engine's interface, `export type Topo = { ... }` then `declare module 'claude-code' { interface EngineInterface { topo: Topo } }`, with no import or reference, its exported names led by the noun's PascalCase name (`Topo`, `TopoRun`), named in `plugin.json` as `"types": "./types/index.d.ts"`. The plugin's own hooks module imports those types from that file, so the contract is the one place they are written. A plugin that depends on it never copies the file: it lists that plugin under `dependencies` in its own `plugin.json`, and each time the engine loads it from a folder it lays types in (above) it lays that plugin's contract into `.claude-plugin/types/<plugin>/index.d.ts`, so the noun is typed on the dependent's `$`; `claude plugin validate` checks the contract.

## Developing one

A mod made in this session goes where SKILL.md's WHERE TO WRITE IT says and loads as it describes. The rest of this section is the other ways a plugin under development is run from disk; how other people get a mod is under Sharing a mod.

`claude --plugin-dir <folder>` loads the plugin from disk for that session only (repeat the flag for several). `CLAUDE_CODE_PLUGIN_DIRS` names the same folders where no flag can be given (a session the desktop app or an SDK host starts): one or more absolute paths (`~` allowed) separated by the platform's path-list separator, each loaded exactly as a `--plugin-dir`, taken from the process environment or the `env` block of `~/.claude/settings.json` (never a project's settings). In an interactive session the folder is watched, as is a plugin auto-loaded from a skills folder (`~/.claude/skills/<name>`, the project's `.claude/skills/<name>`): saving a file reloads the hooks module, so
`register` runs again in a fresh environment and the previous environment's timers are dropped. A save that leaves a loaded file holding the text it was loaded from reloads nothing (after a reload that failed, any new save tries again). Saves made while the session's own turn runs (the model editing the plugin) reload once, when the turn ends, or sooner when a tool or command the plugin registered is about to run, so the turn can try what it wrote. Saves from anywhere else reload once the folder has been quiet: a lone save within a quarter second, a run of saves seconds apart once the run stops. A headless `claude -p` always loads fresh, and a long-lived headless session (SDK, desktop) watches too when `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` is set the same way, its reload lines reaching the host as `ui_log` messages and the debug log.  
Options for a plugin loaded this way are read from settings under `pluginConfigs`, keyed by the plugin's `<name>` (or `<name>@inline`); each non-secret `userConfig` field is a row in the config menu too, and a change there reloads the module with the new `options`. A `string` field that lists `options` (`"options": ["gist", "turbo"]`, its `default` among them) is a picker over exactly those values there, and a stored value outside them counts as unset.

An installed plugin is read from one of two places, and `/reload-plugins` re-reads that place. A plugin whose marketplace is a folder (`claude plugin marketplace add <folder>`) and whose entry there is a relative path (`"source": "./mods/tally"`) is read from that folder itself, never from the copy `claude plugin install` made: edit the folder, run `/reload-plugins`, and the reload names it and the folder when the folder changed since the session last read it (`<plugin>@<marketplace>` re-read from its folder: `<folder>`), in a terminal and in a session the desktop app hosts on this machine alike, with no new version and no reinstall; `claude plugin update` says it is read from its folder when the folder holds the version on record, and `claude plugin list` shows the folder (`Read from:`). Every other installed plugin runs the copy made when it was installed (a git, npm or archive source, a marketplace fetched from a repository or a URL): an edit to a working copy reaches a session only as a new version or commit, through `claude plugin update` and then `/reload-plugins`. The folder a reload or the list names is the one the session runs: where that is not the working copy (the desktop app keeps a plugin saved from an upload in a folder of its own), add the working copy's folder as a marketplace and install from it, or name it in `CLAUDE_CODE_PLUGIN_DIRS`. A plugin folder given as a link is watched at the folder the link names.

Run with `claude --debug` while developing. A hook that fails is skipped and the chain continues without it, unless its registration's `.catch` handler
answers in its place. So a hook that guards (one whose answer refuses a tool call, a prompt, a command, a setting, another plugin) is written `on(...).catch(($, e, next) => next.called ? next(e) : { deny: 'why' })`, `{ deny: 'why' }` standing for the event's own refusal, which its doc in the types shows: where the hook had not called `next` the handler refuses, and where it had, `next(e)` replays what that call settled to and nothing runs twice, so a guard judges before it calls `next` (at `tool.check`, where `next(e)` only reads the verdict and runs nothing, the handler answers `{ decision: 'deny' }` either way). Without the handler, what the guard judges goes on when it throws, answers a wrong shape or outlasts its budget; a handler that itself throws leaves the hook skipped too. While the session hot-reloads a plugin folder (the mods folder once hot reloading is on, a `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` folder an interactive session watches) the transcript says a hook was skipped, once, in a dim line naming the
plugin, the event and the reason, as it names a module that did not load, and in any other session that line goes to the debug log alone, as `<plugin>: <line>` (a `claude -p` run has no transcript: one printing text names a `--plugin-dir` plugin whose module was not loaded, or failed to load, once on stderr with the reason, the switch being off included; a json or stream-json run keeps it in the debug log). The debug log has a line for every occurrence and each result the engine
refused; a skipped hook's line has the error's name and message length in place of its text (the first one's text, cut to a short line, is on that transcript line, which the debug log has too), so a plugin that seems to do nothing has usually been told why. `claude plugin test <folder>` runs the plugin's `*.test.ts` files against the engine itself: a test holds the engine's `$` and an `on` whose hooks sit beneath the plugin (import `test`, `expect`, `mock` from `claude-code/testing`; the typings say the rest). Nothing sits beneath those hooks (but the kit's own bottom for `$.state` and for `session.append`, which answers a plugin's `$.session.append` as a session stores or refuses the row, and a row the test raises with the blocks a session pins put back; `mock.session(on)` reads the rows back): they stand for the engine, so what one answers reaches the plugin as given, fields only the engine sets included (a `tool.call` answer's `isReadOnly`, and its `ref` and `text` when the plugin relays it), while every plugin in the test, wherever it stands, is read as in a session. A test gives the plugin under test its `userConfig` values with `test(name, { options }, body)`, which it reads as the values stored in settings (a value outside a field's `options` unset, defaults filled in, then validated); left out, the plugin gets its manifest's defaults. A UI test mounts a component through the plugin on a surface it names, never an assumed one (the kit's `mount` on the test's `ui` noun: `{ plugin, surface, component, props }`), and acts on the drawing by key (`press`, `input`, `find`, a `Client`'s `key` and `post`), each act typed by that surface's element table; write the body once and loop it over `['terminal', 'desktop'] as const` so the test shows the plugin does not depend on one surface. A tree the test drew through the engine's `ui` noun (`render`) is acted on the same way through that noun's `press`, `input` (`{ plugin, key, text, kind? }`: `change` is one edit reaching `onInput`, `submit`, the default, is Enter reaching `onSubmit`) and `select` (`{ plugin, key, value }`); every act resolves only once the chain, the element's own handler and any work that handler left running unawaited have settled, so a test asserts right after the `await` with no settling of its own (work asleep on the mocked clock waits for the test to advance it). The test's `classic` noun raises a classic hook event as the engine does (`SessionStart({ source: 'clear' })`, the envelope fields stamped unless given; every event but `PreToolUse`, which a test reaches through the `tool` noun's `call`: `$.tool.call` raises `classic.PreToolUse` as a session does, beneath every plugin's `tool.call` hook and above the test's own, so a deny ends the call with the errored result a session's `tool.call` hooks see (`isError`, the reason as `text`; `{ deny }` to a plugin's own `$.tool.call`) and the test's hook never runs, while a rewrite, a pass, an ask or an allow goes on; with no settings hook configured, no decision stands beneath the test's own `classic.PreToolUse` hooks. Where a plugin or the test hooks `tool.check` for the tool, the call then raises it as a background subagent's loop does, with no prompt to show: the question carries the call's `tool_use_id` and any `agentId` the test gave (`$.tool.call({ tool: 'Bash', command: 'ls', agentId: 'a1' })`), never `isReadOnly` or `ceiling`, which a test states on `$.tool.check`, as nothing of the host runs under a test; a mod's `$.ui.ask` states `isReadOnly` on the call it raises; what passes down the chain is what PreToolUse settled, else an allow; a test's `classic.PermissionRequest` hook answers a plain ask, and none refuses it; the test's own `tool.check` hooks are asked again of an input that hook rewrote, an ask there refusing the call; a hook's `decider: 'person'` is refused, so a test can't play a person allowing it). The kit exercises the plugin's hooks and the description they return under each surface's rules, not any surface's paint.

## Sharing a mod

This is the GitHub road: a repository people install the mod from. Where the paragraph of SKILL.md that begins THIS SESSION names another way to share, that way comes first, and this road is for people outside the person's organization or for when the person asks for a repository; where it names none, this is the way to share.

One file makes a mod's repository a marketplace, and another person then installs the mod with one line, typed at the prompt of a terminal session:

`/plugin install <mod> --marketplace <owner>/<repo>`

That line is the install step: the one to give the person, and the one a README's install section holds, in a code block, with what follows it (`y` to add the marketplace, then a scope). `claude --plugin-dir` and `CLAUDE_CODE_PLUGIN_DIRS` (Developing one) are how a mod under development is run from its folder.

`<mod>` is the `name` in the mod's `plugin.json`, and `<owner>/<repo>` a GitHub repository that holds a marketplace file, `.claude-plugin/marketplace.json`, listing the mod. The shortest such repository is the mod's own folder, the marketplace file written beside `plugin.json`, its one entry's `source` the repository's root:

```json
{
  "name": "<marketplace>",
  "owner": { "name": "<author>" },
  "plugins": [{ "name": "<mod>", "source": "./" }]
}
```

A mod written in this session is first copied out of the session's mods folder to a folder the person keeps, and that copy is made the repository. `claude plugin validate <mod folder>` reads the marketplace file, the manifest and the hooks module in one run.

**Making the repository.** With the person's yes, and opening, printing or searching no file in the mod's folder until the scan in step 5 has run (where it cannot run, none at all):

1. Where the person has not said public or private, ask whether the repository is public (anyone can read the code and install the mod) or private (only people the person invites on GitHub, who also need GitHub set up on their own computer to install the mod), in those words, and create nothing until they answer.
2. Agree with the person on the `<owner>/<repo>` to create: the GitHub account or organization it goes under, and its name.
3. Run `gh auth status`. Where `gh` is not installed or not signed in, say so, and do not install `gh` or start a sign-in for them: go on with steps 4 to 6, then in place of step 7 give the person the steps by hand (make an empty repository on github.com, private or public as they chose, with no README or license; then `git push -u <url> main` in the mod's folder).
4. Before writing anything, check whether the folder the person keeps is in a git repository: `git -C <mod folder> rev-parse --show-prefix` succeeds inside one. Where it is, say so, agree with the person on a new or empty folder in no git repository (the same check fails there), and copy the mod into it leaving out every `.git` (`rsync -a --exclude .git <mod folder>/ <new folder>/`, or, without rsync, a copy that skips each `.git` folder). The steps below use that copy, so no repository the person already has is changed.
5. In the mod's folder, before opening any file there, run `git init`, then check that the repository has no history: where `git -C <mod folder> rev-parse -q --verify HEAD` prints a commit, or `git -C <mod folder> for-each-ref` prints anything, the folder already holds git history, which a push would send unscanned, so tell the person, stage nothing, and go back to step 4 to start again in a new folder. Otherwise call the `mcp__plugin-authoring__scan_secrets` tool with the mod's folder, as an absolute path, as `folder`; it reads the files in the folder (not those in `.git`) for known key and token formats, and its answer starts with a `Result:` line. Where the tool is not listed, load it with ToolSearch. The scan cannot run where the tool is still missing, the skill's text says it is not available, the person or a permission rule refuses the call, or the answer is an error, says `Result: the scan could not run`, or has no `Result:` line. For each file it flags, tell the person only the file and the kind of secret, and wait for their word; leave the file unopened for as long as the scan flags it, whatever they decide: no reading, printing or searching it. A file left out stays in the folder, so later scans flag it again. While it stays left out, or the person has chosen to keep it, it needs no new word unless the scan reports a different kind of secret in it. A file the person changed that the scan still flags needs their word again. Where the answer says more files were flagged than it lists, tell the person that too: the share cannot go on while any flagged file goes unlisted, and leaving files out does not lower that count, so the person has to change them or move them out of the folder. Open no file in the folder; once the person has changed the listed files, or they are left out as in step 6 (after its `git add .`), run the scan again, and do the rest of this step (the marketplace file, the README, the validation) only once a scan lists every flagged file and the person has decided on each. For the files and folders it did not scan, tell the person which and why (or the counts, where it lists only some): such a file goes into the commit unscanned unless it is left out. Where it says part of the folder was not looked at, tell the person that files and folders past the first 20,000 were neither looked at nor scanned, and that any of them git commits goes unscanned; they can go on, or start again from step 4 in a copy without the bulky folders. Say both in one message and wait for their word. On a later scan, a file or part of the folder the person has already answered for needs no new word while it is reported the same way. What step 6 leaves out without asking needs no word at any scan. Where it flags `plugin.json`, ask the person for the mod's name. Where the scan cannot run, tell the person why and stop there, even where they say to go on: open no file in the folder, and commit, create and push nothing; skip the rest of these steps, the by-hand ones in step 3 included. Then add the mod's entry to `.claude-plugin/marketplace.json` unless it is listed there already, writing the file where there is none, and an install section holding the lines below to `README.md`, writing the file where there is none. Where either file stays flagged, give the person what to add to it instead. Run `claude plugin validate <mod folder>`.
6. Run `git add .`, then list what is staged (`git -C <mod folder> -c core.quotePath=false diff --cached --name-only`). `.claude-plugin/types/` is usually not listed: the engine writes a `.gitignore` there that ignores the folder. Without asking, leave out what the operating system or an editor made (a `.DS_Store`, an editor's backup), any `.log` file, the `.mcpb-cache/` folder where the engine unpacks an MCP bundle, and `.claude-plugin/types/` if it is listed: with your file-writing tool, not a shell command, write their paths, one per line as git listed them, to a new file in a folder that `mktemp -d` makes; where `test -s <that file>` succeeds (git would take an empty list as every file), run `git -C <mod folder> --literal-pathspecs rm -r -q --cached --pathspec-from-file=<that file>`, then delete that folder; with your file-writing tool, add a line for each to `.gitignore` (only for a file the scan shows as `<name holding a secret>`, to `.git/info/exclude` instead, so the name is not committed), and run `git add .gitignore`. The `tsconfig.json` at the mod's top level stays. Run the scan again, and handle what it flags, what it did not scan, or its failing to run, as in step 5. Read each staged file the scan did not flag, dotfiles included, for what should not travel (a key or token; an internal hostname or URL; a name or data that is someone else's; code or text that belongs to an employer or client: their product, system or project names, or code copied from the project the mod was built in). Where the scan or your read finds any, tell the person the file and what kind of thing it is, never a secret or any part of one, and wait for their word: leave it out the same way, change it (then `git add` it again and run the scan again: once it passes the file, read it like the others; where it still flags it, tell the person and wait again), or keep it. Treat a file you could not read in full (too large, binary, or cut short) the same way: name it and wait for their word. Then run `git add .` and commit, right after the last scan and with no file changed since, and run `git branch -m main`; where git says a branch named `main` already exists, tell the person and stop there, even where they say to go on: change no branch and push nothing. Where git has no name or email to commit with, ask the person for them and set them for this repository alone (`git config user.name`, `git config user.email`). After this commit and before a push has succeeded, where the person wants a change, go back to step 4, agree with the person where the new copy goes, and start again in it. Make each change the person asked for, those before the commit included, in the folder the person keeps first, so the new copy has it; a file the scan flags the person changes themselves. After a push has succeeded, tell the person that updating the repository is not covered here, and stop: never force a push.
7. `gh repo create <owner>/<repo> --private --source <mod folder> --push`, or `gh repo create <owner>/<repo> --public --source <mod folder> --push` where the person chose public. This is the step that sends the code. Where the command is refused, give the person the steps by hand from step 3. Where it made the repository and the push failed, or the repository is there already from an earlier try, give the push alone: `git push -u <url> main` in the mod's folder, with the new repository's URL, and without running the scan again.
8. Give the person the repository's URL and the install lines, ready to paste to someone else, and name each file you left out.

**Install lines for the README.** At the prompt of a terminal session:

`/plugin install <mod> --marketplace <owner>/<repo>`

From a shell:

`claude plugin install <mod> --marketplace <owner>/<repo>`

In the desktop app, where `/plugin` does not run: click + next to the prompt box, then Plugins, Add marketplace with `<owner>/<repo>`, then Add plugin.

A private repository installs only for people who can read it on GitHub and whose machine already holds a git credential for github.com (an SSH key, or `gh auth login` then `gh auth setup-git`): the install never prompts for one.

What the other person sees, in order: `Add marketplace?`, naming the source (`github:<owner>/<repo>`), answered with `y`; the plugin's details, the user scope first among the scopes, chosen with Enter; for a mod with `userConfig` options, a screen that sets them; then, for a mod that is a hooks module alone, a tick and `Installed <mod>. Plugin is now active.`, its hooks running in that session from then on with no reload, and under the user scope in each session started after. A source whose marketplace that person has already added skips the question. The source can also be a git URL or a folder's path. Where the source holds no marketplace file the question stays up and says `Marketplace file not found at` and the path; where the marketplace lists no such name the command answers `Plugin "<mod>" not found in marketplace "<marketplace>"`.

The line is a terminal's: a local session the desktop app starts for its Code tab answers that the command is not available there. A mod installed from a terminal at the user scope loads in that local session too, and its `ui.render` hooks draw for the `desktop` surface.

## Packaging a mod in a chat

This is how a mod built in a chat or a Cowork task in the cloud is kept and passed on, where the skill's SHARING IT paragraph or the cowork-plugin skill's Packaging names it. The mod's folder ends with the session's container, so the mod is handed over in the chat as a plugin file: `<mod>.plugin`, a zip of the mod's files with `.claude-plugin/` at its top, `<mod>` being the mod's name, as its folder and the `name` in its `plugin.json` have it. The chat shows the file as a card. Work through the steps in silence, writing nothing between the tool calls (no "nothing sensitive here", no "validating and zipping"): between the yes and step 5's message the person hears from you only where a step has you tell or ask them something. With the person's yes, and opening, printing or searching no file of the mod's until the scan in step 2 has run (where it cannot run, none at all):

1. Copy the mod's folder into a new, empty folder, as `<new folder>/<mod>/`. ## Drawing: ui.render

A `ui.render` hook receives one component instance. `e.component` says
which component, `e.surface` where it is drawn (`terminal`, `desktop`,
`mobile` or `vscode`), `e.requestId` which instance (the tool_use_id for a tool row or
dialog, the message id for a message or a command's output row, the agent id for a spinner), `e.props`
the component's plain-data props, and `e.viewport`, when the surface has
measured, the size it draws into in character cells: `columns` and `rows`. A transcript message's `e.props.onScreen` says which of its rows the viewport shows now (`{ first, last, of }`, from the site's first laid-out row; `null` while off screen; absent where the surface does not say, as on the terminal's main screen), and the hook re-runs for that message when it changes.  
A change of width re-runs every hooked site once the resize settles, so a
tree sized to `columns` stays right; a change of height alone re-draws
nothing. A `Pane` or `AbovePrompt` hook sizes its tree to `e.props.bodyColumns` instead: the box it draws into, no cell of which lies under a mark of the engine's (its close mark and the band's `[-]` sit outside it), and which is narrower than the viewport while a pane is docked beside the transcript. `e.viewport.isFullscreen` says whether the surface docks a pane at all (the terminal's fullscreen layout does, its main screen opens one inline; absent where a surface does not say, so do not assume), the fact `command.run`'s `presentation` carries, so a plugin opens a pane unasked only where it would be a sidebar. `$.ui.invalidate` asks for a redraw
when the hook's own state changed. State a drawing draws from belongs in `$.state`, not a module variable (a hot reload loses those): named values the host holds for the session, each with a version. Declare them in the contract (`interface PluginState { counter: { count: number; isOpen: StateFamily<boolean> } }`), refer to one by a typed reference whose `plugin` and `key` are literals (`const count = { plugin: "counter", key: "count" } as const`, a const used for nothing but `$.state` calls, the state library's functions and a spread adding a family member's `id`), and read it while drawing: `const { value = 0 } = await $.state.get(count)`. That read subscribes the instance, and a later `$.state.set` draws exactly the readers again, so nobody calls `$.ui.invalidate` for it. A render hook never writes (`$.state.set` while drawing is denied); write from a handler closure or another event, and never from a value the closure captured at draw time: `import { update } from "claude-code"` and `onPress: () => update($, count, n => (n ?? 0) + 1)` reads, applies and writes with `ifVersion`, again on a miss, so two presses before the redraw both land; `atom(ref, initial)`, `derive(sources, fn)`, `memberOf(family, e)` and `read($, source)` come from the same import. Only the owner writes a value; another plugin changes it by hooking `state.set` with a matcher on `plugin` and `key` and passing `next` another `value`. To keep a value past the session, write it to `$.store` too. A value outlives a reload, so new code meets what old code stored: on a key declared `Shaped<T>`, `atom(ref, initial, { shape: 'items-2' })` reads a value stored under any other tag (or none) as `initial`, and writes carry the tag. Your edit first runs after your answer, when the turn ends: a hook of it that fails comes back to you as a notice at your next turn, and starts none; mend the mod then.

Build trees from the table `$.ui.resolve(e)` returns: the surface's element constructors,
destructured into the hook's JSX tags (a module has no element globals). Tables differ per
surface, see `Elements` (`mobile` has no `Input`, `Select` or `Client`, `vscode` no `Client`,
`terminal` no `Svg` but alone `Raster` and `Image`); narrowing `e.surface` narrows the table. A grid of colored cells
(sparkline, heat map, rendered frame) is one `Raster`, its cells packed per `RasterProps`, never a `Box` per cell; `$.ui.blit`
repaints a mounted one without a render pass. A picture (PNG or RGBA bytes, or the name of a file or POSIX shared-memory object another local process wrote, per `ImageProps`) is one `Image` over a box of cells: the kitty graphics protocol where the terminal has it (kitty, Ghostty), iTerm2's inline images on iTerm2 3.5 and later under fullscreen rendering, for bytes (a file or shared-memory name draws its `alt` there), either of these inside tmux too, for bytes only, where tmux has `allow-passthrough` and `focus-events` on, its `alt` elsewhere or where the terminal cannot read this machine's files; a new source updates it in place, and a keyed one is swapped at the frame rate by `$.ui.blit({ requestId, key, source })`, the pixels never crossing `$`. Model-style text (headings, lists, tables, code fences, links; one outside `https:`/`http:`/`file:` draws as text) is one `Markdown`, drawn as an assistant reply is; given `key` and `onLinkPress`, a plain single click on a link it drew (any, or one `pressableLinks` names) raises `ui.press` carrying the link's `href` instead of the surface opening it, where the surface reports clicks (the fullscreen terminal; a ctrl- or alt-click still opens it). Return a
tree, or `next({ ...e, props })` to change what the engine draws, or `next(e)` to leave it.
A hook whose tree does not validate (an element the surface lacks, a prop it does not take, a
child where none goes) has failed, as a hook that returns a wrong shape has: it is skipped alone,
its `.catch` asked; what it had from `next(e)` stands, or, having not called it, the next handler
runs in its place, so every other plugin's part is drawn. The debug log says so, and while the session hot-reloads a plugin folder (the mods folder once hot reloading is on, a `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` folder an interactive session watches) the transcript too, once per load and plugin: `<plugin>: ui.render hook skipped: returned the wrong shape (a tree <Component> refuses: <reason>)`. A tree is judged as the hook answered it, so a `hover` needs its keyed Box in that hook's own answer. Around the question dialog (`AskUserQuestion`) a `Client` the terminal draws counts the rows it drew last, and a hook whose own `Client` takes a tree within the dialog's rows past them is skipped the same way. What is finally drawn is checked whole as well, so rows passed any other way fail there: a tree that fails that is not drawn, the engine draws its own, and the line reads `<plugin>: ui.render (<Component>) refused: <reason>; the engine drew its own`, ending `nothing was drawn` where the engine draws nothing, `<plugin>` being the one plugin whose hook could have drawn the tree, `hooks` otherwise; the debug log has a line beginning `ui.render (<Component>): the chain settled on a tree that does not validate`. A field's key is its plugin's: two plugins may each draw a `key="q"`. An answer that validates and then throws while the terminal draws it (a tree, or an engine component handed a rewritten prop it cannot draw, say a call's row in an expanded tool group whose `ToolUse` `input` has a field left `undefined`) costs that site alone: the engine draws its own there, from its own props, and the session goes on; the debug log says so, and while the session hot-reloads a plugin folder the transcript too, each once per load and component: `<plugin>: ui.render (<Component>) threw while drawn: <reason>; the engine drew its own`, `<plugin>` being the one plugin the draw shows the answer is owed to (a built-in hooked on the same component that never ran, or only handed the draw on, is left out), `hooks` where several had a hand in it or several installed plugins are hooked there, which the engine cannot tell apart. That answer is not tried again; the next one (other props, an invalidate, a reload) is drawn afresh. Where the engine draws nothing, nothing is left: the band above the prompt stays empty and the line ends `nothing was drawn`; a pane is closed and the line ends `the pane was closed`. No tree is refused for the length of a text it draws. (What names a thing is still held to a length, and refuses the tree past it: 10,000 characters for a `Code`'s `language` or `path`, a `Client`'s `key` or `module`, an `Image`'s, `Raster`'s or `Markdown`'s `key`, a `Select`'s or an option's `value`; 2,048 for a `Link`'s address; 131,072 for an `Svg`'s `source`. Around the question dialog (`AskUserQuestion`) a tree is held to its rows, by the surface that draws it: 12 on the terminal, which shows only its last screenful, and 48 on desktop, vscode and mobile, which draw the tree in a frame of their own above their card for the question. Rows are counted the same way on every surface: a text, a `Button`'s or an `Input`'s label and an `Svg`'s `alt` count a row to the line and one more for each 40 columns they come to, a `Select` and what stands in an `Input`'s field one row, being cut at its end. A `Markdown` there refuses the tree on the terminal; desktop, vscode and mobile draw it and count its `text` as any other, by its lines and wraps. No surface takes a width, a height, a position or an offset there, nor a `hover` that reveals or moves, and on every surface the engine's own node stands in the tree exactly once with nothing below it. The painter's own marks (`[ ]`, a hotkey's `1: `) and a label squeezed beside a long value are not counted.) A tree, at any site, draws the first 100,000 characters of its texts in the order written (children, `Code` sources, `Markdown` texts, labels, alts) and ends the text it cut with words saying how much is left out; a `Code` it cut is drawn as plain code. What is carried whole or not at all counts too and gives way where the room ends: a `Link` (by its address) and a `Client` (by its `props`; it unmounts, its state gone) draw nothing, a `Box` loses its `key`, a `Markdown`'s `pressableLinks` become none, every link left to the surface, and a `Button` or a `Select` whose label or any option would not be drawn whole gives way to the words saying how much is left out, or to nothing once they are said, so neither is pressed on words that could not be read. The `value`s of a tree's `Input`s have a room to themselves, as large again, so no text drawn beside a field moves its cut: past it a field starts from its head. It is said as a refusal is (the debug log always, the transcript while the session hot-reloads a plugin folder), once per load and component: `<plugin>: ui.render (<Component>): <n> characters of text are drawn up to the first <m>`. The props a hook rewrote on their way to the engine's own component have their long texts held to as much again, the same way. Their keys and strings of up to 256 characters (an id, a kind) are never altered: a prop that holds more than 100,000 characters of them, or is nested past 32 deep, is drawn as the engine had it, that prop alone, said once per load and component: `<plugin>: ui.render (<Component>): props.<name> rewritten with more than 100000 characters of keys and short strings, or nested past 32 deep; the engine's own is drawn`. To show more, draw the part in view. A registration goes through at any length too and, once through, says what became of the rest, once per op and kind of text, naming the first it is so of: a command's or an agent's `description`, a command's `argumentHint` and a pane's `title` are kept up to 4,096 characters; a tool's `description` reaches the model up to what it is sent of any tool's (4,096, or 16,384 once the model loads the tool through tool search); a tool's `inputSchema` is whole, with a line past 65,536 characters saying it rides on every request. A `$.ui.log`, `$.ui.toast` or `$.ui.status` text draws its first 2,000 characters on the terminal and 10,000 on a remote surface, a `$.ui.notice` its first 2,000. A toast takes the place of its plugin's own toast only, never another plugin's. On the notification bar it waits while another plugin's shows or any waits, in place of its own newest waiting, and alone there it replaces its own; while the bar is held (a `holdToasts` pane, the diff panel) each one raised waits, a plugin's own oldest giving way once 50 of its own do. The stack draws each plugin's newest before any plugin's second newest, so a plugin's newer toast takes its own drawn seat; it holds 50 in all, and past that the oldest toast of the plugin that holds the most leaves. A toast of a plugin in a managed seat (`prepend` or `append`, as the host seated the plugin at load: nothing a plugin or a call of `$.ui.toast` can name) goes in front of every other plugin's. On the bar nothing is moved for it: each toast keeps the place and the time it was given, and so does every line of the engine's own; what changes is whose words fill the toasts' time. A managed seat's words are read first, at once where another plugin's toast is on show, and each toast is read for its own time in all, so the toast it goes in front of has the rest of its time afterwards, and a toast may be read in two parts, either side of one of the engine's lines. When the engine takes time away (one of its lines that shows at once ends the toast on show, or a pane's hold hides it), the loss is the toast's whose own time that was, as it always was: it keeps only the time its place showed another toast's words. A managed seat's toast is never read for less than it would be with no other plugin's toast about. Where the time it took first cannot be given back (its own place is then dropped or hidden, or its plugin raises again), the toast it went in front of is read for the time that is left, and the debug log says what it lost. On the stack a managed seat's toast is seated before the others, which stay up, their timers running, counted on the `+n more` line while they have no seat; and when the toast that fills the stack past 50 is of no managed seat, the one that leaves is the oldest of whichever such plugin holds the most, never a managed seat's, be it the one just raised. One that gives way on the bar before it is shown, or leaves the stack never drawn, is said as a refusal is. A hook's own answer that is one line (a `command.describe` or `config.describe` field, a `config.set` deny, a `prompt.submit` drop, a `turn.complete` text) stands at any length: the prompt is dropped, the change denied, and the engine keeps the text up to its first 4,096 characters, an ellipsis after; a text a hook hands on unchanged is kept as it came. A `context` beside a `prompt.submit` drop is ignored: the drop stands. A `$.audio.speak` text is spoken up to its first 4,096. Each is said as a refusal is, once per load and event: `<plugin>: <event> hook: a drop of <n> characters, kept up to its first 4096`, `<plugin>: $.audio.speak: a text (<n> characters) is spoken up to its first 4096`. Two values are drawn in a lesser form rather than refused. A `Box` whose `borderStyle` is none of the terminal's (`single`, `double`, `round`, `bold`, `singleDouble`, `doubleSingle`, `classic`, `arrow`, `dashed`, `quote`) is drawn with no border, and everything around it draws; the debug log says so, and while the session hot-reloads a plugin folder the transcript too, each once per load and site: `<plugin>: ui.render (<Component>): Box borderStyle "<style>" is not a border style (the styles are ...); the Box is drawn with no border`, a value that is no string told by its kind, `Box borderStyle is a number, not a style name (...)`. And a `Code` under `format: 'diff'` whose `source` does not parse as hunks (a diff cut mid-hunk, one with no `@@` header) is drawn as plain code, as with no `format` and no `startLine`, and everything around it draws; the debug log says so, and while the session hot-reloads a plugin folder the transcript too, each once per load, site (a pane or band by its instance, the transcript's rows of one component together) and Code: `<plugin>: ui.render (<Component>): Code <n> is drawn as plain code, its source not a unified diff: <reason>`, `<n>` its place among the tree's `Code` elements in the order written, `(path "<path>")` after it when it names one; in the tree a `Client`'s surface module draws, `Client <module>:` stands where `ui.render (<Component>):` does, once per load, module and Code. That reason and the
element's props type are the two things to read. Give every Button in a list its own `key`: it defaults to the label, a surface finds a Button again by it after a redraw, and it cannot tell apart two that share one. A Button is `[ label ]` on the terminal, or with `plain` no brackets: `1: label` beside its `hotkey` and the label alone without one, so a one-glyph label is a one-glyph control the focus still inverts; `variant="primary"` marks the main action of several (the terminal draws its `[ label ]` in the accent color, each other surface its own primary look), `"secondary"` or none is the default look, and `plain` wins over it. `role="dismiss"` marks the Button that closes its site, a drawing hint only: the terminal draws it as without, a desktop its native close control. ## The rows a conversation keeps: session.append

`session.append` IS the append: every place the engine adds a row to a conversation it keeps calls it, once, as the row's originator, and its bottom performs the store. The rows are the person's prompt, a slash command's record and output, each block of the model's response, a tool's result and the rows a tool hands over, a prompt or notification folded into a running turn, the reminders and listings the engine injects, a settings hook's or a chain's context, the loop's own nudges, a compaction's boundary and summary, and the notices the transcript shows, in the main conversation and in every subagent's alike (the event's `agentId` names the subagent's loop). The owner of each list appends the rows it originates (the interactive transcript, the headless session, a subagent's run for its opening rows), and the query loop appends every row it makes as the row leaves the loop; what the owner behind a loop receives, what the transcript file stores and what the next request sends are all the row as the chain answered it. Never a progress row, a row that rides one request alone, or a row a load returned (a `--resume`, a teleport, a subagent's saved transcript): loads are not appends. While no plugin hooks the event the call is the store itself.

The event's `door` names the route the row came in by (`prompt`, `command`, `response`, `tool-result`, `tool-message`, `delivery`, `attachment`, `hook-context`, `note`, `compaction`, `notice`, and `queue` for a queue record's text), `origin` who caused it (a prompt's sender, `{ kind: 'model', model }`, `{ kind: 'tool', tool }`, the engine, a settings hook, a plugin), and `uuid` its id in the transcript. Its `message` is the row: `type`, `name` (an attachment's type, a notice's subtype), `role` (absent for a row no request carries), `isMeta`, and `content`, its blocks as the Messages API spells them, so `{ role, content }` of a row a request carries is an API message. All but the message's `content` is pinned: left out, it is kept; changed, the hook fails and is skipped.

A hook rewrites `content` with `next({ ...e, message })`: text blocks (edited, added, dropped, reordered) and a tool_result's `content` and `is_error` (tool_results answered with no `tool_use_id`, one for each the row holds, stand for them in order, and one naming no `is_error` keeps the row's flag); an image or document block may be dropped or moved, not changed or added. Text a hook puts ahead of every pinned block follows the row's leading thinking blocks or tool results, which a request needs first. The bottom puts back what the record depends on: thinking and redacted_thinking blocks, tool_use blocks and every block it does not author, whole and in place, and each tool_result's id and the set of them. Content left empty removes every block a hook may drop: the pinned ones are put back, and a row left with no block at all is stored with the engine's own words for an empty message, `(no content)`, never with what the hook removed. A rewrite of an attachment rendered per request or carrying media keeps the row as made (said in the debug log). `next(e)` resolves `{ message, uuid }` once the row is stored; a hook that answers a row without `next` is skipped and the row is kept: a row the engine appends is never refused. The engine's later edits of a kept row (a tool result cut to its budget, a hint cleared, compaction) are its own business and no append.

In a hooked session a row is stored once its chain has run, a conversation's appends strictly in the order they were made; a row the engine appends from a synchronous callback (a notice) therefore lands after its chain, and the places that read a list back right away (a turn building its first request) wait for the appends made so far. A tool result's structured record beside its tool_result (`toolUseResult`, what the screen draws), the row's timestamps and parent links, and an attachment's payload are stored as made. The message queue's own record of a queued prompt (the transcript file's `queue-operation` entries) is no row of the conversation, but its text passes the event too, under the door `queue`, as `prompt.submit` left it and as a row the conversation never keeps: a plugin that must change a prompt's words everywhere rewrites them at `prompt.submit`, before they are recorded, and one that wants that record alone to differ hooks the door. The door `queue` is raised for every queue record that holds text, a machine-made one (a poll's event) as well as a prompt's; a hook there that throws or takes longer than a second is passed by and the record is written as raised; one that empties the row leaves the record's text empty. A record of what a plugin's own `$.prompt.submit` or `$.command.run` queued is raised under the frames of the hook that made the call, so that hook is not run on it (the re-entry rule). A record made while the hooks modules load at the session's start waits for that load, however long, and is then raised in its turn; one made before that start is raised, or before a module loaded later is in, is written as made. A rewrite at `prompt.submit` is written to the row that holds the prompt, pasted or attached images beside it or not, and `next` resolves to `{ drop }` where the engine has no row to put it on (it masked a credential in the text itself, say). Two submissions take no rewrite of `text`: one that runs a slash command (the event's `command` is `{ name, args }`; a skill or prompt command has not been rendered by then, a built-in that asks the model has run; its typed line is not a row, and the person is told once that the change was left out), and one the person does not see as typed (the event's `isMeta` is true) that starts a turn of its own. Delivered into a running turn, a hidden prompt takes the rewrite like any other, so a mask reaches another session's message or a background task's notification there; the one exception is the engine's own follow-up to something the person chose in the interface (origin `auto-continuation`), which is read as queued. The engine sets both: a hook that leaves either out of what it passes to `next` has it put back, and one that changes it, or sets it where the engine set none, fails and is skipped. A mod that masks what a person sends therefore masks a command's arguments at `command.run` (`next({ ...e, args })`, before the command runs: both of the command's rows and its prompt-history line then hold the arguments as it left them, and `prompt.submit` reads the command's line and `command` as it ran) and a skill's body at `skill.prompt`, and may answer `{ drop }` at `prompt.submit` when the event carries `command`.

`$.session.append({ message: { type, content }, agentId? })` is the same dispatch from a plugin, and it REALLY appends: a user-role row the person does not see as typed (`type: "user"`, stored `isMeta`, the model reads it) or a notice (`type: "system"`, one text block, the model never reads it), of text blocks alone in this release, to the main conversation or to a running subagent's, under `origin: { kind: 'plugin', name }` and door `note`, with an id the engine mints. The row is in the list at once and in a running turn's requests from the loop's next top. The bottom refuses any other row or block, an `agentId` that names no running loop, and a run no plugin may shape (one started with the settings hooks off, or as a delegated observation), with the reason (the call rejects). The stored user row carries the plugin's name as its origin, so a later reader of the transcript knows who appended it. A plugin above may rewrite it like any row, or refuse it by answering `{ deny: reason }` in place of `next` (after `next` the row is stored, and a deny then fails the hook): the call then resolves `{ deny }` and nothing is stored. A hook's answer is what its `next` answered, the row as stored or the refusal from below, unchanged: a different row fails the hook. That is the one row a `session.append` hook may refuse; where an organization seats its policy plugin, the event continues past the person's plugins like the prompt events do.

```js
on("session.append", ($, e, next) => next({ ...e, message: redact(e.message) }))
  .catch(($, e, next) => next({ ...e, message: placeholderFor(e.message) }))
```

## Work that outlives a dispatch

A hook runs inside one dispatch with a budget of its own time (a `next` or `$` call in flight does not count; a `$.clock.sleep` does, so a `turn.step` generator that polls with it pays every sleep from its one budget), and `next.signal` aborts
when that dispatch is abandoned (the user interrupted, another hook settled
first, the budget ran out); anything started for the dispatch should stop
on it. Work meant to outlive a dispatch belongs elsewhere: start it from a
`session.start` hook, which fires once when the session is ready and is
awaited before the first prompt (so a `$.tool.register` awaited there is
listed by turn one), and keep it going with `$.clock.every` and
`$.clock.after`, whose timers run until cancelled or until the module
reloads. If the engine replaces the plugin's copy mid-session without the plugin having changed (the hooks worker was lost), the hook runs again in the fresh copy, its timers and state gone: a `$.prompt.submit`, `$.command.run` or `$.agent.spawn` the hook already made, with the same input, resolves to the first call's result and is not made twice. That covers a call made while the hook is still running, awaited or not, a timer of its own that fires in that time included; a call made after the hook returned (a later timer, a continuation), and one another hook makes in answer to a call of the start hook's, is made again. A subagent the engine interrupted because the copy that awaited it was lost is started again. `$.prompt.submit` queues a prompt that starts a turn of its own once the session is idle (never folded into a running turn; the call resolves as that turn starts, not when it ends), so
background work can wake a quiet session. `$.model.complete({ model, prompt })` runs one text completion with no history on the session's own client and always resolves a result (`ModelCompleteResult`), never a bare string and never a rejection over what the provider did: `isAnswered` with `text` and `usage` (a `ModelUsage`, the four token counts as the API spells them: the one shape `session.compact`'s result, `turn.complete`'s `usage` and the context breakdown's `apiUsage` report a call's cost in too), or `isAnswered: false` with a `reason`, `api-error` (with the HTTP `status` and the `error` kind, never the error's text), `empty-reply`, or `aborted` (its `timeoutMs` elapsed, or the dispatch that made the call was abandoned), `usage` on each arm; only a request the engine refuses to send (a blocked model, a bad `maxTokens`) rejects. `prompt` and `system` each take a string or a list of `{ text, cache? }` blocks (`ModelTextBlock`), sent in order as written: `cache: true` on a block keeps the request up to and including it in the prompt cache, so a mod that sends the same long opening on every call puts that text first and marks its last block, then reads `usage.cache_creation_input_tokens` on the call that wrote it and `usage.cache_read_input_tokens` on the calls that read it within five minutes (both zero: the text is under the model's minimum, or prompt caching is switched off, where the mark is dropped and the text still sent); on Bedrock, Vertex, Foundry or behind a gateway the cached text is found again only while `prompt` opens the same way, so there the fixed text leads `prompt` and is not marked in `system`; marks are not counted, and one more than the API takes comes back as `api-error` with status 400; a hook on `model.complete` is handed the request's `prompt` and `system` as strings, as it always was (a list's texts joined in order), with the lists beside them as `promptBlocks` and `systemBlocks` (`ModelCompleteInput`): the string is what the model is sent, and the marks hold as far as the leading blocks still open it, so a hook that appends keeps them and one that rewrites the opening sends unmarked text. `$.model.fork({ prompt })` asks one tool-less question over the session's own transcript as the main thread last sent it, same model and system prompt, so the API serves that prefix from its prompt cache (`usage.cache_read_input_tokens` says how much it served); its result is the same arms plus `nothing-to-fork` (a new session before its first turn, and again right after a /clear), its `aborted` the turn whose hook forked interrupted while the fork ran. What these calls cost is billed to the session's credentials. A fork counts in the session's cost total and its cost and token metrics as a turn's requests do; a completion and a classification stay out of them, and a completion's `usage` is how a mod counts it (a classification answers only its label). Where OpenTelemetry logging is on, each request also logs an `api_request` event (`api_error` when it fails) naming the mod, third-party names redacted unless `OTEL_LOG_TOOL_DETAILS` is on, with `query_source` `plugin_model_complete` or `plugin_model_classify` (a fork's stays `hook_prompt`). Your `telemetry.log` hook is not handed the event of a completion or classification it made itself, and one made from a timer skips all of your own hooks; a fork's events reach every hook, its caller's too, so a hook that forks on them forks again. `$.ui.status`, `$.ui.toast` and
`$.ui.log` show state without starting a turn, `$.ui.copy({ text, surface })` puts text on the clipboard of the surface the caller names (a press hook passes `e.surface`; left out, the session's first): the terminal's through the machine's clipboard tool and OSC 52 (not sent in a VTE terminal once the tool has started, nor ever to VTE before 0.53), resolving `{ isCopied: true }`; `{ isCopied: false, reason }` on a remote surface, or when no tool ran and OSC 52 was not written, as in VTE before 0.53 with no clipboard tool, `no-clipboard`, or with nothing drawing, `no-surface`; the event `ui.copy` carries the target `surface`, so a hook may rewrite, refuse or take it), `$.ui.notify(text, { title })` raises a native notification by the person's own channel (their `preferredNotifChannel` setting, after their classic `Notification` hooks ran reading `plugin_notification`; headed by the plugin's name when no title is given), resolving `{ isSent: true, channel }`, or `{ isSent: false, reason }`: `disabled` when they turned notifications off, `no-channel` when their terminal has none, `no-surface` where the session holds no terminal (a `-p` run, the SDK, the desktop: the hooks alone run) or none is bound yet or the process is exiting (a call at the module's load, or in a `session.end` hook after a SIGTERM: nothing runs), `refused` when a hook on `ui.notify` answered `{ value }` without sending (a hook's `{ deny }` rejects the call instead); `terminal_bell` as the channel means a bell alone, no text shown; `$.store` keeps values
across sessions, `$.session.version()` answers the engine's `version`, its `base` release and its `builtAt` build time (the values the engine's own analytics rows carry, in every mode and build), and `$.process.run` runs a host command by argv. `$.fs` reads (text, or `{ as: 'bytes' }` for `{ base64 }`), writes, lists and stats paths; `$.fs.stat(path, { resolve: true })` also answers `realPath`, every symbolic link and `..` resolved (what `realpath` gives: a hard link, a `/.vol/` file-id spelling or a case alias keeps its own spelling), so a guard's robust form is an allow-list on `realPath` under a root it resolved the same way, and a deny-list on spellings is best effort.

`$.ui.view({ agentId })` puts an agent's transcript in the main view, as the
person's own switch from the tasks list does; `agentId` is the agent's `id`
in `$.agent.list()`, and `$.ui.view({})` goes back to the main conversation.
It moves the view only while the call answers the person's own input (a
Button they pressed, a field or a pick of theirs, a prompt or command they
typed), because the viewed agent takes the prompt's next Enter; from a
timer, a load or a turn it resolves `{ deny: 'not person-initiated' }`. It
resolves `{}` once the view shows the agent, or `{ deny }` saying why not:
no agent holds the id, the tasks list shows the person no row for it, the
agent is a teammate that was stopped or runs in a terminal pane of its own,
the view was switched again meanwhile, or the session draws no main view
(`-p`, a headless host). An argument that is neither `{}` nor `{ agentId }`
rejects. A `Pane` or `AbovePrompt` hook reads the view in force as  
`e.props.view`.

`$.ui.selection()` answers what the person last selected with the mouse in
the fullscreen terminal, `{ text, requestId? }`: the text as a copy would
take it, and the transcript row it lies in, by the id that row's `ui.render`
reads as `e.requestId` (absent when it spans several rows or lies outside
the transcript). A key or a click takes the highlight down before a command
or a press runs, so the answer stays what they last selected until they
select again, dismiss it, or their next prompt or command has run: a command
they type, or a Button they press, reads it. A prompt typed while a turn
runs and folded into that turn is no run of its own: the selection stays
kept until the next one has run. In a session a host runs headless (the
desktop app) the answer is what the person has selected in the host's page,
asked of every attached client that said it answers selection reads, the
first selection to arrive taken. It
resolves `undefined` with nothing selected, and wherever the engine sees no
selection (fullscreen off, `-p`, a remote surface whose client answers no
selection reads). A command that quotes the selection into the prompt:

```js
export function register(on) {
  on('session.start', async ($, e, next) => {
    await $.command.register({
      name: 'quote',
      description: 'Quotes the selection into the prompt.',
    })
    return next(e)
  })
  on('command.run', { command: 'quote' }, async $ => {
    const selected = await $.ui.selection()
    if (selected === undefined) return { text: 'Nothing is selected.' }
    const quoted = selected.text.replace(/^/gm, '> ')
    await $.prompt.fill({ text: quoted + '\n\n', mode: 'insert' })
    return { text: 'Quoted the selection.' }
  })
}
```

`$.prompt.fill` leaves the caret past the text for `insert` and at the end for `replace` and `append`. Pass `cursor` to stand it elsewhere: an offset into the whole draft after the write, counted as the `cursor` it answers with, whatever the `mode`. An offset out of range clamps. `$.prompt.fill({ text: 'Dear ,', cursor: 5 })` leaves the person typing the name.

To repaint between keys, on a timer or a model's answer, `$.prompt.paint({  
text, decorations })` sets this mod's own decorations and touches nothing
else. It answers `isPainted: false`, with the box as it stands, when the draft
no longer reads `text`, or the mod may not read it, so call `$.prompt.read`
too. With another mod hooking `prompt.read` it always answers false, painted
or not. An empty list clears. Other mods' paint stands. The draft's next change
drops it, so a timer repaints after every key.

## Tools and agent types the model can call

`$.tool.register` declares a tool: its name, the description the model
reads and its input schema; the tool is listed as `mcp__<plugin>__<name>`.
The engine places it behind ToolSearch, as it does an MCP server's tool: the
model sees its name and loads the schema when it asks. `isDeferred: false` in
the spec puts the schema in the prompt's tool list from the start, which is
what a mod whose own tool the model should reach for wants; a `tool.describe`
hook's `isDeferred` is read ahead of the spec's.
The plugin serves it by hooking `tool.call` with the matcher
`{ tool: 'mcp__<plugin>__<name>' }` and returning the result, and a call
no hook answers fails saying so. Registering the same name again replaces
the tool, and a plugin may register several, each listed as it lands. `$.agent.register` declares an agent type the same way, `<plugin>:<name>`, from an agent definition as settings JSON spells one (prompt, tools, model, and the rest, all in force); a plugin folder's `agents/*.md` files declare them too. `$.agent.spawn({ subagentType })` runs one and its answer is its `turn.complete`; an `agent.offer` hook returning `{ isOffered: false }` keeps it from the model while the plugin's own spawn still runs it.
